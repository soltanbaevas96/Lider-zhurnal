# AUDIT_BEFORE_FIX.md
Технический аудит проекта «Лидер+» (CRM учебного центра).
Дата аудита: 2026-08-10. Аудит **только диагностический** — правки не вносились.

---

# Project overview

Веб-CRM для учебного центра «Лидер+» (Павлодар). React + Vite SPA, backend — Supabase
(Postgres + Auth + RLS + RPC + Storage + одна Edge Function), хостинг Vercel с авто-деплоем
из GitHub (`main`). Роли: `admin`, `director`, `teacher` (+ подтип «куратор» через таблицу
`curators`), `assistant`, `office_manager`, `senior_office_manager`.

**Главный системный вывод аудита**, определяющий все остальные разделы: репозиторий содержит
только 4 SQL-файла (`01_schema.sql` … `04_lessons_count.sql`), описывающих раннюю версию схемы
(только роли `teacher`/`admin`, без офисов, кураторов, оплат, зарплат). Реальная production-база
по словам владельца прошла миграции **до №37**, и фронтенд (`src/lib/api.js`) вызывает **40
RPC-функций** и работает с таблицами/колонками (`office`, `lang`, `capacity`, `rate`,
`curator_id`, `_issued_logins` и др.), которых в репозитории просто нет. То есть: **актуальная
структура базы и почти вся серверная бизнес-логика существуют только внутри Supabase и нигде не
задокументированы и не версионируются.** Это не единичная проблема, а рамка, ограничивающая
глубину проверки безопасности ниже — RPC-функции проверены только «снаружи» (как их вызывает
фронтенд), их SQL-тело недоступно для ревью.

# Architecture

```
index.html → src/main.jsx → src/App.jsx (роутинг по ролям)
                              ├─ src/pages/*.jsx      (24 файла — экраны/кабинеты)
                              ├─ src/components/*.jsx (7 переиспользуемых компонентов)
                              └─ src/lib/
                                   ├─ api.js       — ВСЕ запросы к Supabase (772 строки, единая точка входа)
                                   ├─ auth.jsx     — контекст авторизации, флаги ролей
                                   ├─ supabase.js  — клиент (anon key из VITE_*, без хардкода)
                                   └─ utils.js     — форматирование, транслит, периоды, палитра
```

Слой данных дисциплинирован: **все** обращения к Supabase из страниц/компонентов идут только
через `src/lib/api.js` (кроме `auth.jsx`, что ожидаемо). Ни одна страница не дёргает
`supabase.from/rpc` напрямую в обход `api.js` — это хорошая практика, облегчающая ревью.

Есть отдельная Supabase Edge Function `invite-teacher` (Deno) — единственное место, где
используется `service_role` ключ (на сервере, не во фронтенде — корректно).

# API

`src/lib/api.js` — единственный модуль доступа к данным, 772 строки, ~90 экспортируемых функций.
Хорошо сгруппирован по разделам (справочники, уроки, посещаемость, зарплата, оплаты, расписание,
кураторы, админ-функции). Часть операций (CRUD над `students`, `groups`, `teachers`,
`attendance`, `lessons`, `curators` — простые insert/update/delete) выполняется напрямую через
`supabase.from(...).insert/update/delete`, полагаясь целиком на RLS. Часть — через **40 RPC**
(`supabase.rpc(...)`), где вся логика (расчёты зарплаты, дашборды, права) выполняется на
сервере — это правильный паттерн для тяжёлых агрегаций, но означает, что корректность и
безопасность этой логики нельзя проверить статическим анализом фронтенда.

# Auth

`src/lib/auth.jsx`: сессия из `supabase.auth`, профиль подгружается из `profiles`, дополнительно
проверяется наличие карточки в `teachers` и `curators` (роль `teacher` + карточка `curators` →
флаг `isCurator`). Вход по логину: нелогиновый ввод (без `@`) резолвится в email через RPC
`email_for_login` (`SECURITY DEFINER`, из `03_students_attendance.sql`, `grant execute ... to
anon, authenticated` — сделано осознанно и корректно, т.к. до логина пользователь ещё не
`authenticated`).

Создание учётки преподавателя — через Edge Function `invite-teacher`: **проверка роли
`admin` на сервере выполнена правильно** (клиент передаёт JWT вызывающего, функция сверяет
`profiles.role === 'admin'` через anon-клиент с этим JWT, и только после этого использует
`service_role` для создания пользователя). Утечки `service_role`-ключа во фронтенд не найдено.

Несоответствие с `CLAUDE.md`: в `invite-teacher/index.ts` технический email строится как
`login@lider.local`, а `CLAUDE.md` описывает домен `лидер-plus.kz` (`login@lider-plus.kz`).
Либо документация устарела, либо в проде используется более новая версия функции, не
попавшая в репозиторий, — см. блок про RPC/миграции выше.

# RLS

Только по старой схеме (`01`, `03`), актуальность на проде не подтверждена:

- `profiles`: `select using (id = auth.uid() or is_admin())`; `update using (id = auth.uid())`
  **без отдельного `with check`** и без ограничения по колонкам.
- Справочники (`subjects`, `groups`, `teachers`, `assistants`, `students`, `student_groups`,
  `teacher_groups`, `teacher_subjects`) — читают **все `authenticated`** без какого-либо
  скоупинга (`auth.role() = 'authenticated'`), пишет только `is_admin()`.
- `lessons`, `attendance` — админ всё; преподаватель — только свои (через `my_teacher_id()`).

Более новые таблицы (`curators`, `communications`, `audit_log`, `schedule`, `student_events`,
платежи) — RLS-политик для них в репозитории нет вообще (появились в миграциях 05-37, которых
нет в репо). Проверить их фактические политики можно только напрямую в Supabase Dashboard.

# Storage

Один bucket — `lesson-plans` (приватный, `public: false`). Политики: `select`/`insert`/`update`
разрешены **любому `authenticated`** пользователю без привязки к владельцу файла или уроку.
Пути — случайные UUID (`crypto.randomUUID()`), что затрудняет угадывание, но не создание
списка объектов бакета (если `list`/`select` на `storage.objects` не ограничен — а он не
ограничен). Отдельных политик `delete` не найдено вообще — по умолчанию Storage delete
запрещён, если политика не создана явно, так что это, вероятно, не проблема, а просто нет
функции удаления файлов планов в принципе.

# RPC

40 RPC-функций вызываются из фронтенда, из них **только `email_for_login` имеет SQL-определение
в репозитории**. Остальные 39 — включая самые чувствительные:

- `admin_set_role(p_profile_id, p_role, p_office)` — меняет роль/офис любого пользователя;
- `admin_set_password(p_profile_id, p_password)` — принудительная смена пароля любого пользователя;
- `admin_create_account(p_kind, p_card_id, p_login, p_password, p_role)` — создание учёток;
- `admin_soft_delete(p_kind, p_id)` — мягкое удаление сущностей;
- `get_account_info(p_profile_id)` — возвращает, судя по UI (`Manage.jsx:858`, `info.password`),
  **пароль в открытом виде** (что соответствует известному, задокументированному в `CLAUDE.md`
  дизайн-решению — дублирование пароля в `_issued_logins`, т.к. bcrypt необратим);
- `add_payment` / `delete_payment` / `get_students_payments(p_office)` — финансовые операции;
- `get_payroll` / `close_payroll` / `reopen_payroll` — зарплата.

**Ни одно из этих определений не находится под контролем версий.** Нельзя подтвердить или
опровергнуть статическим анализом, что `admin_set_role`/`admin_set_password`/
`admin_create_account` сами проверяют `is_admin()` внутри функции (что обязательно, если это
`SECURITY DEFINER`, а иначе они не смогли бы обходить RLS для чужих профилей). Это ключевая
точка для верификации напрямую в Supabase SQL Editor (см. P0 ниже).

# Security vulnerabilities

**P0-1. Возможная эскалация привилегий через `profiles.update` (RLS).**
В `01_schema.sql:117`: `create policy "profiles self update" on profiles for update using (id =
auth.uid())` — без `with check`. В Postgres RLS для `UPDATE`, если `with check` не задан явно,
используется то же выражение `using`. Условие проверяет только **какую строку** можно менять
(свою), но не **какие колонки/значения**. Если эта политика не была позже сужена (в миграциях
05-37, недоступных в репозитории) или не защищена явным `with check` / триггером, любой
авторизованный пользователь потенциально может выполнить
`supabase.from('profiles').update({ role: 'admin' }).eq('id', myId)` прямо из браузерной
консоли и стать админом. **Нужно немедленно проверить в Supabase Dashboard → Authentication /
Database → Policies, действует ли всё ещё эта версия политики, до любых других правок.**

**P0-2. Внутренняя защита `admin_*` RPC не верифицируема.**
`admin_set_role`, `admin_set_password`, `admin_create_account`, `admin_soft_delete` — их SQL-тело
не в репозитории. Если они помечены `SECURITY DEFINER` (что необходимо для смены чужого пароля/
роли в обход RLS) и **не содержат внутри себя проверку `is_admin()`**, то любой авторизованный
пользователь, зная имя функции и сигнатуру (они видны в `api.js`, публичном фронтенд-коде),
может вызвать `supabase.rpc('admin_set_role', {...})` напрямую и назначить себе роль `admin`.
Проверка на стороне фронтенда (скрытая вкладка «Управление») **не является защитой** — это
чисто UI-гейтинг.

**P1-1. Офисный скоуп `office_manager` реализован только на клиенте.**
`OfficeManagerCabinet.jsx` тянет **все** записи (`fetchAllStudents()`, `fetchAllGroups()` —
без параметра офиса) и фильтрует по офису в JS (`if (s.office !== office) return false`,
строки 87 и 154). Если RLS на `students`/`groups` — унаследованная от `01/03` схема
(`auth.role() = 'authenticated'`, без офисного скоупа), то офис-менеджер одного офиса технически
может получить полный список учеников/групп **всех** офисов через прямой вызов
`supabase.from('students').select('*')` из консоли браузера, в обход UI-фильтра. Это прямое
нарушение бизнес-правила «офис-менеджер — только свой офис» и потенциальная утечка персональных
данных учеников других офисов.

**P1-2. Офисный параметр в `get_students_payments(p_office)` передаётся с клиента.**
`fetchStudentsPayments(office)` передаёт `office` как обычный аргумент RPC. Если функция сама не
проверяет, что `p_office` совпадает с офисом вызывающего (для не-старших офис-менеджеров), то
офис-менеджер может запросить **платежи чужого офиса**, просто изменив параметр — это уже
финансовые данные учеников, более чувствительные, чем справочники.

**P1-3. Пароли сотрудников хранятся в открытом виде (`_issued_logins`).**
Задокументировано в `CLAUDE.md` как осознанное решение (bcrypt необратим, поэтому пароль
дублируется отдельно для показа админу). Технически это означает: при компрометации БД или
при неаккуратной RLS-политике на `_issued_logins`/`get_account_info` пароли **всех** сотрудников
раскрываются в открытом виде одним запросом. Не новая находка, но фиксирую как системный риск —
доступ к этой функции должен быть заперт строго на `is_admin()`, и это стоит перепроверить
вместе с P0-2.

**P2-1. Storage `lesson-plans`: нет владельческого скоупа.**
Любой `authenticated` может читать/загружать/перезаписывать любые файлы бакета (не только свои
уроки). Риск ниже, чем у P1, т.к. пути — случайные UUID, но `select`-политика на `storage.objects`
потенциально позволяет перечислить все объекты бакета.

**P2-2. CORS Edge Function `invite-teacher`: `Access-Control-Allow-Origin: '*'`.**
Не критично (эндпоинт всё равно требует валидный JWT админа), но `*` шире необходимого —
можно сузить до домена `lider-zhurnal.vercel.app`.

**Не найдено:** service_role ключ во фронтенде, хардкод API-ключей/секретов, `.env`-файлы в
репозитории, SQL/command injection паттерны (весь доступ через supabase-js query builder и RPC
с именованными параметрами).

# Data integrity issues

- **`communications.author_name`** сохраняется как свободный текст (`addCommunication(...,
  authorName)`), а не как `profile_id`/foreign key — запись в журнале общения может быть
  подписана произвольным именем, не связанным с реальным автором действия. Ослабляет
  достоверность аудиторского следа.
- **Дубли-призраки** учеников/групп с пустым `office` — известная, задокументированная в
  `CLAUDE.md` проблема прошлых импортов; статус на текущий момент не проверялся (требует SQL-
  запроса к проду, вне рамок статического аудита).
- Схема в репозитории (`01-04_*.sql`) не отражает текущее состояние — само по себе это уже
  проблема целостности между «source of truth» (прод) и версионируемым описанием.

# Performance issues

- `fetchDictionaries`/`fetchAllDictionaries`/`fetchAllStudents`/`fetchTimesheetData` тянут
  студентов/связки `student_groups` с `.limit(100000)` целиком на клиент при каждом открытии
  соответствующих разделов — уже сейчас (1197+ связей, по `CLAUDE.md`) это, вероятно, заметная
  нагрузка на клиент/сеть. Основные тяжёлые агрегации (дашборд, аналитика, зарплата) уже
  корректно вынесены на сервер через RPC — это правильно и снижает риск. Точечные `from()`-
  выборки справочников остаются наименее оптимальной частью, но не критичны при текущем объёме.
- `OfficeManagerCabinet` грузит **всех** студентов/группы всех офисов и фильтрует в JS —
  дублирует и проблему безопасности (P1-1), и лишний трафик.

# Technical debt

**Главная находка раздела: в репозитории одновременно живут три поколения одного приложения.**

1. **Актуальная и используемая версия** — всё, что импортируется из `src/main.jsx` →
   `src/App.jsx` → `src/pages/*`, `src/components/*`, `src/lib/*`. Только это реально
   собирается и деплоится (подтверждено чтением `index.html`, `main.jsx` и сверкой импортов).
2. **Мёртвые дубликаты верхнего уровня** — корневые `App.jsx`, `components/`, `pages/`, `lib/`
   (вне `src/`). Не подключены нигде (`vite.config.js` не переопределяет root, entry — только
   `/src/main.jsx`). Более старая версия того же кода (например, в корневом `App.jsx` нет
   `OfficeManagerCabinet`, `Control`, ролей office_manager/senior_om — см. diff, снятый в ходе
   аудита).
3. **Мёртвые дубликаты внутри `src/`**: `src/Analytics.jsx`, `src/Dashboard.jsx`,
